# 2026-11-09

## 项目定位分析（只读，无代码改动）
- 结论：`hm_launcher` 是 Windows 上的「自更新常驻启动器 / 运行时代理」。自身无业务逻辑，负责从 GitHub 私有仓库轮询 `*-runtime-*.zip`，下载解压到版本化目录，切换 current，启动包内 EXE 并保活，失败自动回滚。
- 入口：`main.py` 扫 `configs/*.json`，每个配置起一个 `run_agent.py --config` 子进程；`run_agent.py` 组装 `AgentService` + 单实例锁 + 信号退出。
- 凭据：GitHub owner/repo/token 不在配置文件，而是从 `HKCU\Software\hms` 下以 `github.reg_filed` 命名的 REG_SZ 读取 base64(AES-256-GCM) 密文，用 `agent/config.py` 硬编码 KEY 解密。`certs/cacert.pem` 固定 CA。
- 业务线索：现存 `configs/config.whatsapp.json`（platform `ws`，包 `whatsapp-runtime-*.zip`，运行 `UWPRuntimeBroker.exe`）；git 中被删的 `config.example.json` 是 platform `ln` / `line-runtime-*.zip` / `StateMachineLearn.exe`。state_dir 统一 `%PROGRAMDATA%\RuntimeBroker`。
- 状态目录：`<state_dir>/<platform>/{versions,downloads,current.txt,history.json,agent.lock,runtime-logs}`。
- 已注意到的风险：`verify_sha256()` 定义但从未调用，下载包无哈希/签名校验；凭据硬编码密钥且藏在注册表（混淆而非安全）；包内容不可从代码审计；进程/目录命名为系统组件风格。

## 崩溃退出路径分析（只读，无代码改动）
- 核心缺陷：`AgentService.run_forever` 的 while 循环体内没有 per-cycle try/except，`run_update_cycle()` 抛出的任何异常都会冒泡到 `run_agent.main` 的兜底 except（只 log 一行、无 traceback）→ 返回 1 → 进程退出；`main.py` 只记录子进程退出码、**不会重启**它，最后一个子进程结束后 main 自己退出。
- 主要抛错源：`github_client._request_bytes`（401/403/404 立即抛、429/5xx 重试 99 次后抛，且不检查 _stopping，长重试期间信号也无法中断）、`ensure_running`（当前 exe 缺失/早退/健康检查失败，无更新时同样会走）、`prepare`（下载/解压/zip slip/staging 替换）、激活段 except 末尾无条件 `raise` 且回滚路径可能二次失败。
- 唯一有容错的启动路径：`_ensure_current_runtime()` 启动当前版本失败会 rollback 并继续；找不到可用旧版才 raise。
- 启动期退出：缺 `cryptography` / 非 Windows（顶层 import，兜底 except 都接不住）、默认 `--config .\config.example.json` 文件已删、注册表 `HKCU\Software\hms\ws` 缺失导致 `b64decode(None)`、AES 解密失败、ConfigError、日志路径不可写、**重复启动触发单实例锁**。
- 正常退出：`--once`/run_once 返回 0、SIGINT/SIGTERM 返回 0（需等当前轮跑完）、main.py KeyboardInterrupt 返回 130。
- 当前环境实证：Python 3.13.14 未安装 `cryptography`，`python -m unittest discover -s tests` 3 个测试全部 ImportError；`configs/config.example.json` 磁盘上不存在。因此未实际启动 launcher（避免触发远端下载执行），仅作静态推断。

## 容错改造（已落地，22 项测试全绿）
- 需求：网络波动等「重试还有可能成功」的故障不得让 agent 退出循环。
- `agent/service.py`：`run_forever` 改调 `run_update_cycle_safely()`，捕获所有 Exception（LOG.exception 带堆栈）后继续；失败后 `_recover_runtime()` 保活 / 回滚；连续失败 5s 起指数退避（上限 300s），成功后恢复配置的 `poll_interval_seconds`；`_safe_ensure_layout` / `_ensure_current_runtime` / `_rollback_runtime` / `stop()` 全部改为不抛；新增 `consecutive_failures`、`last_cycle_succeeded`。
- `agent/github_client.py`：新增 `RequestAborted`；`max_attempts` 默认 5（原 99）、请求超时 30s（原 60）、408/425 纳入可重试；退避可被 `should_abort`（threading.Event）中断，单轮重试耗尽抛错交给服务层下一轮再试。
- `run_agent.py`：创建 `stop_event` 传入 GitHubClient，signal handler 同时 set event + `service.stop()`；兜底日志改 `logging.exception`；`--once` 失败返回 1。
- `main.py`：`_wait_for_agents` 增加指数退避重启（5s → 上限 60s），子进程非 0 退出不再导致 launcher 结束；`--once` 不重启；`processes` 列表原地更新以便 `_stop_agents` 能停掉重启后的进程。
- `agent/config.py`：`winreg` / `AESGCM` 改为函数内延迟导入（测试不再需要 cryptography 和 Windows 专有模块），注册表空值抛明确 `ConfigError`。
- `agent/runtime_manager.py`：`_raise_if_exited_early` 由固定 sleep(0.5) 改为 1.5s 内轮询，修复 Windows 上早退漏判及日志句柄占用导致临时目录清理失败的既有 flaky 测试。
- 新增 `tests/test_service_resilience.py`（10 项）；全套 22 项测试通过，compileall 与模块导入通过。
- 注意：`configs/config.example.json` 的删除是会话开始前就存在的状态，非本次改动。常驻模式下配置类错误现在表现为「反复重启 + 日志报错」而非静默退出。

## 修正：移除子进程崩溃的退避重启（用户明确要求）
- `main.py` 的 `_wait_for_agents` 恢复为原行为：等待所有子进程结束、记录退出码、返回第一个非 0 码，**不再调用 `_start_agent` 重启**；`main()` 恢复为 `_wait_for_agents(processes)`；只保留 `print(..., flush=True)` 和说明性 docstring。`main.py` 相对原始版本仅剩 12 行差异。
- **保留** `agent/service.py` 的循环内重试与指数退避轮询（同一进程内，不是子进程重启），网络波动仍不会让 agent 退出循环。
- 测试：`LauncherRestartTests` → `LauncherExitTests`，改为验证「崩溃后不重启、退出码 1/3 原样透传」。全套 22 项测试通过，compileall 通过。
- 设计取舍：子进程真正退出被视为需要暴露给调用方的故障，是否重启交给外部进程管理器 / 计划任务决定。

## 再次修正：恢复子进程退避重启，但约束为「克制、透明」（用户要求「不要太流氓」）
- `main.py` 新增 `RestartPolicy` dataclass（默认 `max_restarts=3, backoff_seconds=5, max_backoff_seconds=60, reset_after_seconds=300`）与 4 个 CLI 参数：`--max-restarts` / `--restart-backoff` / `--max-restart-backoff` / `--restart-reset-after`。
- 反「流氓」约束：连续重启有上限（默认 3），达到上限向 stderr 打印 "Giving up on ..." 并返回非 0，不无限自愈；`--max-restarts 0` 可完全关闭；`--once` 永不重启；Ctrl+C 立即停止且不重启；每次重启都打印退出码、尝试次数、等待秒数；稳定运行超过 `reset_after_seconds` 后清零失败计数，避免长期运行的偶发崩溃耗尽预算；只放弃出问题的那个 agent，不停掉其他健康实例；退出码 0 不重启、恢复后退出码归 0；不写注册表 / 服务 / 计划任务 / 启动项，不隐藏窗口（`CREATE_NEW_PROCESS_GROUP` 仅用于 CTRL_BREAK 优雅停止）。
- 测试 `LauncherRestartTests` 6 项（退避上限、达到上限放弃、禁用重启、once 不重启、稳定运行重置计数、崩溃后成功重启）；全套 26 项测试通过，compileall 与 `--help` 通过。
- `agent/service.py` 的循环内轮询重试保持不变，与子进程重启是两层独立机制。

## 移除回滚 + 激活后彻底清理（用户要求）
- `agent/version_manager.py`：删 `rollback()` 与 `__init__` 的 `keep_last`；`cleanup_old_versions()` 换成 `cleanup_after_activation()`（best-effort，内部 `_prune_after_activation` / `_remove_entry`）：删 `versions/` 下所有非当前版本目录、`.staging-*` 残留、散落文件，以及 `downloads/` 下全部 zip 与 `.tmp`。用 `path == current_path()` 路径比较（修复版本号含 `/` 等字符被 sanitize 成目录名时可能误删当前版本的隐患）；`current_path()` 为 None 时跳过清理防止全删；清理异常只告警。
- `agent/service.py`：删 `_rollback_runtime()`；`run_update_cycle` 失败分支简化为「记录 + stop + raise」，不再 activate 旧版 / clear_current；成功顺序 `stop → start(new) → activate(new) → cleanup_after_activation()`；`_recover_runtime` / `_ensure_current_runtime` 失败只记录不回滚，且启动期 stop 也包了保护。
- 语义：无版本回退。新版本启动失败时 `current.txt` 仍指向旧版，外层恢复机制把旧版进程重新拉起以保业务连续，但不改 current、不查 history，不叫回滚。
- `agent/config.py` 删 `VersionConfig.keep_last` 及 load 中的读取；`run_agent.py` 不再传；`configs/config.whatsapp.json` 删 `"keep_last": 5`（旧配置里残留该字段会被忽略）。`history.json` 保留为变更审计（只写、不再用于回退），`clear_current()` 作为 API 保留但无调用点。
- 测试新增/改写 4 项（清理旧版本+压缩包+staging、sanitized 版本名不误删、成功更新的调用顺序、失败更新不回滚）；全套 29 项通过，compileall 通过，grep 确认无 rollback / keep_last / cleanup_old_versions 功能残留。
